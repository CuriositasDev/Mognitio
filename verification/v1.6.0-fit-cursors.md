# Small allocation search cursors

Large live collections can leave a long prefix of small free blocks. Repeated
requests for a larger common object rescan that prefix even when the fitting
tail changes only by splitting. Whole-project lowering exposed this behavior
while decoding and independently comparing long escaped literals.

The allocator now remembers incoming free-list links for the 16 aligned physical
sizes from 40 through 160 bytes. A remembered prefix contains only blocks too
small for that exact request. Allocation can only remove or shrink those blocks.
When a link's containing block is allocated, all affected cursors move to its
incoming link. Collection clears every cursor before coalescing can change link
locations. Other sizes use the ordinary search from the head.

The selected block, split boundary, free-list order and heap partition remain
identical to first-fit. There is no additional heap ownership or managed root.
Private context metadata is revision 8, with a fixed 128-byte cursor table;
the independent metadata and heap snapshot readers retain explicit layouts.

The tests in tests/v160-fit-cursors.lisp execute the emitted search instructions
against an independent ordered-block oracle. They cover all cached sizes, larger
uncached requests, splits, consumption of cursor-owning blocks and deterministic
mixed requests. A 256-block undersized prefix followed by 256 fitting requests
requires at most 512 block probes. Disabling cursor reuse violates that bound;
removing cursor repair violates first-fit equivalence. Existing native collector,
heap geometry, stress, resource and metadata tests remain required.

These changes support the ongoing compiler work. They do not replace an existing
frozen seed or establish completion of the expanded native compiler. A new seed
must be accepted and frozen separately before dependent compiler evidence is used.
