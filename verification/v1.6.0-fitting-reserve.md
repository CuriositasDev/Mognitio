# Fitting reserve for fragmented large heaps

A 65,536-element List build exceeded the 900-second exploratory cutoff after
the inherited C1 RSS repair. Independent physical free-list inspection found
166,491,728 free bytes but no block large enough for an 8,240-byte request:
the largest of 423,426 free blocks was 4,096 bytes. Aggregate free space hid
the shortage, causing repeated collections instead of reserve growth.

For default heaps above 256 MiB, reserve accounting now counts only blocks
that can satisfy the current physical request. Smaller heaps retain aggregate
accounting: applying the filter unconditionally regressed the unchanged old C1
check to 300,630,016 bytes RSS. The selected guard restores that check to
243,892,224 bytes in 94.59 seconds, within its existing 256-MiB criterion.
Reserve fraction/cap, first-fit order, explicit geometry/caps, minimum arena,
and optional-mapping failure fallback are unchanged.

The same large List build completes in 319.78 seconds at 1,379,143,680 bytes
RSS. Its generated ELF is byte-identical to the earlier successful label-index
candidate and exits 104. These exploratory observations are not formal samples.
