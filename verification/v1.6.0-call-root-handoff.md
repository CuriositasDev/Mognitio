# Call argument root handoff

A forced-collection retention observation found that an Err payload survived,
but its dead parent Result was still retained by the caller's call-site roots.
This violated the required lifetime boundary during result reconstruction.

Source calls now pass a hidden trailing bitmap. The caller keeps its before-call
roots while transferring arguments; the callee first installs its own parameter
and capture roots, then switches the caller to the after-call bitmap excluding
the not-yet-produced output. No allocation occurs during this transition.
Standard I/O adapters follow the same protocol. Startup and argument-free template
calls explicitly disable the handoff. Runtime constructor helpers retain their
existing protocol.

Both independently implemented root validators check the new bitmap. Synthetic
call, field-call and non-call plans reject 11 corruptions covering dead arguments,
an overwritten output, a missing live caller value, shape and spurious handoff.
The existing 152-CFG / 456-mutation differential suite also passes.

[Evidence identities](v1.6.0-call-root-handoff.json) include:

- Six normal/observed retention cases: String and product/List Err payloads;
  direct/nested closure captures of runtime Strings and containers.
- Independent physical heap graphs show the original parent Result reclaimed
  before the new Err constructor, with the same payload and a new descriptor.
  Nested closure cases reclaim the old maker and environment while the reader
  remains the only path retaining its captured value.
- Two deliberately retained-parent controls execute normally but are rejected
  by the retention witness; no crash or missing stress counts as rejection.
- Metadata, whole-IR, dataflow, concrete, closure, helper, native, root and capture
  source-origin probes all pass. Native runtime passes 90 observations.
- Reversing actual concrete requests (including differing type interning order)
  produces byte-identical executable pairs, both with the expected runtime exit.
- The freshly generated S9 candidate passes eleven functional gate groups,
  including runtime, review cases, inherited behavior, faults, resource lifetime,
  and isolated execution in two supported userlands.
