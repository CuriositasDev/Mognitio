# Allocation reserve after collection

A nearly full live heap could reclaim only a few blocks. Because one allocation
then succeeded, arena growth remained suppressed and subsequent short-lived
objects triggered repeated full collections.

After a failed free-list lookup and collection, default allocation checks the
total free space and replenishes reserve below one quarter of mapped bytes,
capped at 64 MiB. Growth remains at most once per allocation attempt, with the
existing 1 MiB minimum. Explicit arena geometry and heap caps retain their
previous behavior. A failed optional reserve mmap retries reusable blocks, and
successful reserve growth preserves first-fit selection.

The [observations](v1.6.0-allocation-reserve.json) identify the tested compiler.
Retaining 10,800 cells while replacing 100,000 cells now takes five collections,
against 4,763 with fixed 1 MiB geometry. Both execute 121,605 allocations and
return the expected values. The reserve increases mapped memory from 1 to 2 MiB.
The larger retained-graph test remains under its independent 160 MiB bound:
20 collections and 149,082,112 mapped bytes, versus 178 collections with fixed
geometry. These counts are operational regression controls, not formal timing
budgets.

Fault injection confirms that optional reserve mmap failure still returns the
correct result through reuse; initial arena, metadata and later required
allocation failures retain the allocation-failure diagnostic. Existing
first-fit equivalence and cursor mutation tests pass.

The complete normal suite passes 238 groups, 605,763 assertions, 1,322 native
processes and every subsequent Python integration. Compiler/test source was
checked at 25d72e550843f089d35d81b7ad177f439fe77119; the following record commit
adds only these two verification documents. Whitespace checks pass.
