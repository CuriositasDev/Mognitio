# Physical arena lookup in the Lisp native runtime

Whole-compiler generation reaches large live heaps containing many allocation
arenas. The collector's exact allocated-start validator previously scanned every
arena row for each managed reference. This repeats a linear search throughout
each collection, although the physical index is already rebuilt independently.

Sort complete arena-index rows by unsigned physical base in the existing
collection workspace. Search that index with an upper-bound binary search, then
check the selected range, alignment, allocated-start marker and allocated header
before dereferencing the candidate. Static-object lookup is unchanged. Moving a
row preserves its own size and allocated-start bitmap pointer.

Heap geometry, reserve and growth caps, first-fit allocation, collection
scheduling, workspace capacity, descriptors and public behavior are unchanged.
The in-place insertion sort depends on arena count; the repeated pointer lookup
depends logarithmically on arena count. No managed allocation or additional
workspace is introduced by the sort.

## Independent checks

The new Lisp tests interpret actual emitted operations against an independent
address map. Sorting is compared with independently ordered complete rows, and
pointer classification with linear exact-start association. Cases include empty
and non-power-of-two indexes, reversed and interleaved input orders, range ends,
gaps, alignment, free starts and addresses across the signed-word boundary. The
address map rejects unmapped reads, including premature candidate dereferences.
The search-comparison bound is checked independently. Wrong-search and
wrong-bitmap negative controls must fail these oracles.

Existing native invalid-pointer, static-root, transitive-lifetime, reclamation,
allocation-geometry and optional-reserve-failure tests remain required. Larger
retained-graph diagnostics compare allocation, collection and mapped-byte
counters separately from wall time. Increasing reserve caps is a separate
experiment and is not part of this change.

## Seed and acceptance boundary

Run the cumulative suite and record its exact tested revision in the change's
pull request. This runtime change does not mutate an existing bootstrap seed.
After accepting the implementation increment, freeze a new seed identity from
the integrated source, verify every component, restore and reject mutations,
and repeat witness, profile and complete-compiler capacity qualification.

Rebuild dependent compilers and their required acceptance evidence from that
qualified seed. A private source build or binary-patch diagnostic is not a seed
qualification, accepted compiler generation or formal performance measurement.
Whole bootstrap, inherited performance envelopes, final-candidate measurements
and release remain separate gates.
