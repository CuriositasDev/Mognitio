# Exact-size cursor cache for large allocations

Repeated medium-size allocation requests could rescan the same long prefix of
small free blocks. A 330-second diagnostic sample of the previous compiler
concentrated over 90% of samples in two instructions in that scan loop.

The allocator now keeps 32 bounded, direct-mapped cursor entries for physical
requests larger than 160 bytes, alongside the existing 16 small-size entries.
Each entry checks the exact requested size; a collision clears the old cursor.
Consumption and splitting repair every affected cursor, and collection clears
all cursor pointers before coalescing. The original first-fit order is retained.
The private context grows by 512 bytes to 944 bytes, or 992 in test images.

The independent ordered-block oracle covers mixed sizes, hash collisions,
cursor-owner removal and repeated prefixes. Disabling reuse preserves results
but violates the probe bound. Omitting exact-key comparison or owner repair
violates the oracle. Native large-string workloads pass with a bounded heap,
both normal collection and collection before every allocation. The independent
heap-snapshot reader pins the new geometry and retains all existing corruption
controls.

[Observations](v1.6.0-large-fit-cache.json) identify the exact tested source.
The normal suite passes 242 groups, 1,889,890 assertions, 1,324 native processes
and every subsequent Python integration. The isolated full-backend compiler
passes 90 native observations and 41 generation/execution cases in each of two
minimal Ubuntu userlands without the compiler toolchain or sources.

The 168-file compiler input, with the existing full-backend driver harness,
completes lower in 325.71 seconds with exit 0 and empty output. This is an
exploratory observation with concurrent checks, not a formal timing budget or
a final-candidate acceptance result.
