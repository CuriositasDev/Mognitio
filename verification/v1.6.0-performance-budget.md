# Complete-backend performance budget

status: accepted
adopted: 2026-10-18

This budget applies only to the frozen candidate and all 103 named cells in the
[machine-readable record](v1.6.0-performance-budget.json). Candidate, seed, source
inventory and fixture identities must match. It does not alter inherited gates.

[Complete preliminary observations](v1.6.0-preliminary-performance.md) informed
purpose-specific waiting and resource envelopes. Values are not automatic
multiples of maxima or the 900-second / 4-GiB preliminary guards.

The JSON maps each cell explicitly; exceptional build groups include paired
negative fixtures. Each run must be correct. The median of three recorded wall
times and their maximum RSS must satisfy the criteria; warm-up and recorded
runs all obey the independent cutoff. RSS polling is not an OS hard limit.

Small generated inputs use short feedback envelopes. Full projects use bounded
batch envelopes. Maximum List literals deliberately use a separate batch class
with a 2-GiB acceptance envelope. This exposes observed compiler growth without
claiming that public List-operation complexity guarantees bound compiler time.

Reclamation uses the fifteen frozen lifetime observations: bounded and I/O
mapped bytes at checkpoints must stay within 2 MiB and collector-reported live
bytes within 4 KiB, with mapped spread at most 1 MiB within each count series.
The retained positive control permits at most 256*n + 2 MiB for both values
and requires at least fourfold growth across each tenfold count increase.
These are fixture-specific controls, not object-layout guarantees. Final owned
resources must be zero; observed descriptor maxima are three for bounded/retained
and four for I/O. Functional stress and retention witnesses remain separate.

Formal acceptance requires new serial 1+3 measurements and fresh lifetime
observations after adoption, using the same candidate and fixtures. The budget
record does not claim those executions have happened. No release is authorized.
